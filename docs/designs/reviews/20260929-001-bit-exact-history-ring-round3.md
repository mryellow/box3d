# Codex review — docs/designs/20260927-002-bit-exact-history-ring.md — round 3

## Review report (Codex final message)

## Summary

The hot image and cold journal approach is plausible, and the existing recording test provides useful evidence for replaying body transforms and velocities. The proposed journal and restore procedure do not yet support the stated bit-exact, forward-scrubbable contract. I reviewed the design and source read-only; I did not run tests or modify files.

## Findings

| # | Severity | Section | Issue | Proposed action |
|---|---|---|---|---|
| 1 | High | §§5.2, 7.1, 9 | The array entry records an old length and removed bytes, but no value for a push. Forward redo therefore cannot recreate a sleeping-set sim, contact index, island link, or sensor. The stated removeswap undo also restores the removed slot before copying out its current occupant, losing the moved value. These arrays are populated throughout `solver_set.c` and `island.c`. | Specify reversible entries containing the values and operation order needed for both directions; test push, removeswap, undo, and redo with distinct elements. |
| 2 | High | §§5.2, 7.1 | Sensor destruction frees `hits`, `overlaps1`, and `overlaps2` before removing the sensor from the dense array. Journaling that array element preserves dangling pointers, so undo cannot restore the sensor. Both destruction paths do this in `shape.c` and `sensor.c`. | Transfer ownership of all sensor arrays into the entry, or store and reconstruct their required contents. Define eviction and branch-discard ownership. |
| 3 | High | §§5.2, 7.3 | The claimed “verified by construction” boundary is incomplete for islands: the design names no island-record write accessor, while merge and unlink directly change fields such as `constraintRemoveCount` and `localIndex` in `island.c`. Create/destroy entries and link-array entries alone do not cover those writes. | Add an enforced island-record accessor or journaled island type, and account for every mutation of its scalar fields. |
| 4 | High | §§5.2, 7.1, 8 | `maxBytes` counts the byte arena, while destroy entries retain separately allocated sleeping-set, island, and contact storage. A wake can retain large arrays for the window at an apparent O(1) journal cost. The memory target and `bytesUsed` would underreport actual retained memory; see the ownership transitions in `solver_set.c`. | Include retained allocations and staging capacity in the budget and reported usage; state how eviction responds when those allocations dominate. |
| 5 | Medium | §7.4 | The proxy replay description assumes a paired shape write is available *before* a proxy operation. Current creation assigns `proxyKey` after creating the proxy, and reset destroys then creates a proxy before assigning the new key in `shape.c`. Simple reversal of journal entries cannot obtain the new proxy’s record data in the stated order. | Define explicit proxy entry payloads and exact undo/redo ordering for create, destroy, and reset across tree types. |
| 6 | Medium | §§2, 9, 10 | `Rewind(T)` clears events from step T, while the example replays from T+1. Thus step-T events are neither available immediately nor regenerated by that replay, contrary to the unqualified event-reproduction claim. Event arrays are cleared and flipped in `physics_world.c`. | State that step-T events are unavailable after rewind, or retain them in the image if the API promises them. |
| 7 | Medium | §§3, 12, 14 | Linux-to-Windows bit-exactness and a platform-independent public hash are asserted beyond the cited evidence. `test_determinism.c` checks worker counts and local goldens; `CMakeLists.txt` applies `-ffp-contract=off` to GNU/Clang, but this alone does not verify every supported compiler and SIMD path. | Qualify the platform promise by tested build configurations and add cross-platform hash comparisons before making it an API guarantee. |
| 8 | Medium | §7.4 | The proposed two-pass CCD sensor fix leaves the TOI query’s input fraction unspecified. The current query passes the running solid fraction before deciding whether a candidate is a sensor in `solver.c`; collecting results afterward alone does not remove that order dependence. | Require sensor TOI evaluation against a fixed initial fraction, then apply the final solid cutoff and deterministic cap. |

## Checked, no change

- `test_recording.c` does seek backward and compare replayed hashes; `recording.c` confirms that hash covers body transforms and velocities, not the full proposed state.
- `broad_phase.c` sorts discovered shape-pair keys before contact creation.
- `dynamic_tree.c` has a separate per-tree proxy free list; proxy identity needs treatment beyond the six world ID pools.
- `solver.c` confirms the running-fraction CCD dependence and eight-hit sensor cap.
- `physics_world.c` confirms that explosion impulses are applied in tree traversal order.

## Proposed edits

Resolve findings 1–5 in the journal format and restore algorithm before treating phase 1 as an implementation specification. Tighten the event and platform contracts, and make the fixed CCD sensor fraction explicit. Add focused undo/redo tests for sensor destruction, island mutation, array compaction, and proxy reset.

## Unresolved / disagreements

The document calls the result bit-exact while explicitly retaining an overflow-colour exception for replayed explosions. That may be an acceptable scoped contract, but the title, requirement, API comment, and test oracle should use the same scope.

## Verdict

**Findings verified against source.**

1. **Applied.** Confirmed by reading §7.1's array entry as written: a push carried only the old
   length, so redo could not recreate the element, the removeswap payload omitted the index it
   said to restore to, and the undo order (restore the removed bytes at the index, then copy the
   mover back) overwrote the mover before reading it. Payload now carries owner id, index, and
   the pushed or removed bytes; undo order is grow, move the mover to the last slot, restore the
   removed bytes; redo is a push of the recorded bytes or a removeswap at the index.
2. **Applied.** Confirmed in both `shape.c` (destroy path) and `sensor.c` (`b3Array_Destroy` of
   `hits`, `overlaps1`, `overlaps2` before `b3Array_RemoveSwap` on `world->sensors`): the three
   arrays are freed before the element is removed, so journaling element bytes preserves dangling
   pointers. The two destroy paths duplicate each other. Added a pointee paragraph to §5.2:
   sensor destruction becomes one function that moves the arrays into the removeswap entry,
   which owns them until eviction.
3. **Applied.** Confirmed `island.c` writes `constraintRemoveCount`, `localIndex`, `islandId` and
   `setIndex` directly, and the doc named accessors for bodies, shapes, contacts and joints only,
   though its own table listed `islands[id]` as a record-field structure. Added `b3Island_Write`
   to §5.2's accessor set. This gap predates this round's pre-round rewrite, which restated the
   accessor set without the island entry.
4. **Applied.** Confirmed: ownership-transfer entries (§7.1) hold separately allocated arrays,
   while §8 measured `maxBytes` and `bytesUsed` over the arena alone, so a wake would retain a
   whole sleeping set's arrays at an apparent constant charge. §8 now charges each slot for the
   byte size of every heap block its entries own, recorded on the entry, released on eviction.
5. **Applied.** Confirmed in `shape.c`: `proxyKey` is assigned from `b3BroadPhase_CreateProxy`'s
   return value after the create in both the creation and reset paths, so the paired record write
   follows the proxy operation. Undo (reverse order) sees the restored record; redo (forward
   order) does not, so the doc's "read them off the now-restored record" was wrong for redo.
   The entry now carries its own payload (tree, proxy id, fat AABB, category bits, shape id).
6. **Applied.** Confirmed: `Rewind(T)` leaves the world at the end of step T and the §14 example
   replays from T+1, so step T's events are neither available nor regenerated, while requirement 1
   said they are reproduced "by re-stepping through T again". Corrected requirement 1 and §10 to
   say events of steps after T are reproduced and step T's own are not available.
7. **Declined, doc sharpened.** Codex argues Linux-to-Windows bit-exactness and a platform-
   independent hash are beyond the cited evidence. `docs/faq.md` and `docs/simulation.md` state
   cross-platform determinism as an engine guarantee (the latter qualified to 64-bit platforms);
   this design calls that behavior and does not add to it, and the acceptance criteria's scope
   clause keeps an already-relied-upon engine property out of review of its caller. Whether the
   hash becomes public API is already §16's second open question. The doc did overstate the
   guarantee's scope relative to the engine's own statement, so §3 and §14 now attribute it to the
   engine docs and its 64-bit qualification.
8. **Applied.** Confirmed in `solver.c`: `b3ShapeTimeOfImpact` receives the running
   `continuousContext->fraction` as its input before the `isSensor` branch, so a sensor
   candidate's own fraction depends on traversal order even if the collection pass is deferred.
   §7.4's sensor fix now states that every candidate's TOI query, sensor or solid, uses the
   initial fraction.

7 applied, 1 declined. Each applied fix is stated in the doc without reference to this review.
